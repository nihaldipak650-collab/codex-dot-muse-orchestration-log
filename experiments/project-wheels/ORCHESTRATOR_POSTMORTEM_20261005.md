# 4. 最严重的 10 个低效点（按影响排序）

1. **正式目标完成后没有硬停止。**配额 100/100 后，计数仍从 118（含 18 个预留）长到 221，形成 121 个文学预留。B04–B10 又新增 75 个计入池的候选；Muse B10 另有 1 条因直链取不到而待定。它比任何单次点击都更影响总任务量。
2. **DOT B09 完成后续发太晚。**12:04 可见回包，13:22:53 才发 B10，空泡 78:52；中间有 12:53 才打开 CSV、13:05 才下 MD、13:08 才完成轻审的留痕。应当先用摘要做快筛并续发，然后下载/整理。
3. **把两个 worker 的轻审排成串行。**Muse B06 10:14:28 已完成，DOT B06 的结果处理延续到 10:23:51，Muse 到 10:30:50 才收到 B07，空闲 16:22。Muse B07 11:26:29 完成后又到 11:37:29 才发 B08，空闲 11 分钟。
4. **附件流程没有抽象成一次取件。**B04 DOT 对 CSV 做了重复打开、DOM 点击、滚动、多个快照、下载，再关闭并另找 MD；B09 DOT 找到 CSV 后隔近 57 分钟才打开。一个单批交付被拆成十几次小动作。
5. **连接和页面身份依赖反复确认。**共享会话短暂只列出 Muse，随后重新打开 DOT_WORKER、检查标题、找 RUN_ID、刷新。安全确认是必要的，但没有稳定的 tab/message handle 和批量读取动作，导致每次都从页面状态重新定位。
6. **发送确认的重试边界不够严。**早期 DOT B01 的日志明确记了同一 RUN_ID 出现两条用户消息，worker 复用了一个结果；Muse B04 又有首次提交及同 RUN_ID 的 `retry1` 提交文件。B04 记录不足以证明页面最终显示了两条消息，但也不足以证明首次未送达。后续 B06 DOT 做得更好：只提交一次，刷新并确认 RUN_ID 出现，没有再发。
7. **把“补完每个状态文件”放在 worker 续发之前。**候选行去重与 RUN_ID 状态必须及时；完整 review Markdown、batch log、CURRENT_STATE、STATE 和 gap narrative 无需在 worker 空闲时一份份刷新。
8. **把仍开放的 gap 当成继续搜索的充分理由。**候选收集阶段不能证明“集成闭环已实现”；因此如果 gap 只有在深验证后才会关闭，逐批搜索就会永远找到更细的缺口。
9. **计数字段语义不统一。**例如 Muse 的 `generated=4` 同时另报 6 个筛除项；B09/B10 又把 worker 历史重复单列。若不统一 screened/retained/excluded/duplicate 定义，协调端必须回头拆数，边际收益也容易被误算。
10. **批次与检查点日志记录时间不总是发送时刻。**多个 `06_AGENT_RUNS.jsonl` 发送时间晚于 `raw\send-*.json`；事后不容易分清 worker 真正完成时间、协调端取件时间与记账时间，削弱了流水线审计能力。

# 6. Browser 微操作浪费

对 `raw\` 文件名按操作类别统计（文件总数 539；类别可能重叠，部分操作命名不一致，因此它是留痕计数，不等于 Playwright API 的精确调用总数）：

| 类别 | 留痕数 |
|---|---:|
| browser_find | 64 |
| browser_snapshot | 50 |
| browser_tabs select | 50 |
| browser_wait | 30 |
| refresh | 20 |
| composer find | 22 |
| click | 10 |
| open attachment | 29 |
| download | 22 |
| reconnect / reopen | 5 |
| identity check | 24 |

真实序列常见为：

```text
select tab → 核对 URL/title → find RUN_ID → 找 composer → submit
→ 再 find RUN_ID → wait → refresh → 再检查
→ 找 COMPLETE → 找 CSV → open → snapshot/read → download → close
→ 找 MD → open → snapshot/read → download
```

B04 的 DOT CSV 在 22:20–22:26 间出现多次打开/点击/快照/下载，接着才开 MD；B09 的 DOT CSV 在 11:56 找到，直到 12:53 才打开。必要动作是首次确认正确线程、发送前查 RUN_ID、对模糊发送结果做幂等确认、取回候选和规范去重。额外动作来自每次都重查整页、反复开预览而不是直接取附件、CSV 表格和 Markdown 分别处理，以及没有一个高层命令封装 `select+identity+read tail` 或 `open+download`。发送延迟确认后的刷新是防重复所需，不能简单删掉；应把等待和复查收进一次有明确成功/失败结果的 RPC。

# 8. Ledger / bookkeeping 调度问题

我确实把本批结果拆写成 review 文件、主表、batch log、gap、run log、CURRENT_STATE 和 STATE。项目主账 232 行中，221 行是计数候选（207 个普通 `CANDIDATE_UNVERIFIED` +14 个 reserve），另 11 行是 coordinator preflight、条件项或 rejected 记录；状态里的 221 因此可以与主账对上，但必须保持这些口径不混算。

**必须在续发前立即保存的最小状态：**RUN_ID 与发送/回包状态；候选 canonical key、来源、所属方向；V1/V2/本批重复标记；明确计入池的数量；下一批是否改变方向。用一个 append-only JSONL/小型批次表 checkpoint 一次写完即可。

**可在 worker BUSY 时延后：**完整 Markdown 叙述、ACCEPTED/REJECTED 的人类可读说明、总 batch history、CURRENT_STATE 全文、重复展开的 gap 描述和总量重算。下一批完成后再批量汇总，或每两批更新一次；不能让 worker 空闲等待叙述性文件同步。

# 10. 新的 TWO-LANE PIPELINE

```text
时间 ─────────────────────────────────────────────────────────────────▶
DOT   █████ BUSY Bn █████ → READY → TRIAGE → SEND Bn+1 → █████ BUSY █████ ……
Muse  █████ BUSY Bn █████████ → READY → TRIAGE → SEND Bn+1 → █████ BUSY ……

协调端  预写两份 NEXT_RUN_DRAFT
        → 谁 READY 就先读谁的摘要
        → 30–90 秒 FAST TRIAGE
        → 立即给同一 worker 发下一批
        → 在 worker BUSY 时下载、规范化、去重、checkpoint、更新 gap
        → 继续处理另一条 lane
```

DOT/Muse 各自维护 `CURRENT_RUN / NEXT_RUN_DRAFT / STATUS / LAST_RESULT / NEXT_GAP`。谁先回就先续谁，不等另一方“凑齐一轮”。找不到附件不影响从正文直链做轻审和续发；只有搜索方向错误、严重重复、输出无法解析、用户判断门槛、达到停止条件或真实连接阻断才暂停该 lane。

# 11. 新的高层动作设计

| 高层动作 | 一次调用内部完成 | 返回给协调端 |
|---|---|---|
| SEND | 复用已绑定线程；首次/恢复时核对准确 URL/title；检查唯一 RUN_ID；提交一次并异步确认。发送不确定时刷新并两次确认不存在后才可重发。 | RUN_ID、message id、sent/uncertain |
| POLL | 对精确线程等待 15–30 秒并只读尾部状态，逐步退避；不反复搜索全页。 | BUSY/COMPLETE/ERROR 与最后更新时间 |
| FETCH_BUNDLE | 下载一个主文件；失败一次后回退到正文行，不重复开多个预览。 | 文件路径或 `INLINE_FALLBACK` |
| FAST_TRIAGE | 检查项目方向、明显无关/坏链接、canonical 重复和数量；目标 30–90 秒。 | keep/drop/duplicate 计数、是否能续发 |
| DEEP_PROCESS | worker 已重新 BUSY 后再处理上一批完整行、重复表和 gap。 | 候选行及批次详细记录 |
| CHECKPOINT | 原子追加 run 状态、计入候选 canonical keys、gap delta 和计数。 | 新 checkpoint id 与计数 |
| RECOVER | 对共享扩展做一次状态诊断；保留 worker/thread 身份；遇到真正阻断时停止重复调用并标明 blocker。 | 两个准确 tab 的状态或明确阻断 |

RUN_ID 是幂等键，**只按“未见”重发，不按“没看到确认”重发**。一次提交后应在后台轮询；只有页面刷新后两次都确认不存在，才可开启一次显式重试。

# 12. Artifact protocol V2

当前真实界面可见的是多个独立 CSV/MD 附件卡片；ZIP 没有经过本次验证，Muse B10 还证明附件预览/下载会失败。因此：

- **DOT（GitHub）：**首选一个 `candidates.csv`，每行一条候选，列带 `RUN_ID, ITEM_ID, PROJECT, ENTITY, CANONICAL_KEY, URL, GAP, FIT, REUSABLE_PART, BOUNDARY, DISPOSITION`；正文固定回报 `RUN_ID / STATUS / SCREENED / RETAINED / EXCLUDED / HISTORICAL_DUPLICATES / GAP_DELTA`。不再附独立长 Markdown；协调端等 lane 已续发后本地生成摘要。
- **Muse（X/YouTube）：**聊天正文必须内嵌短表/TSV，逐条含平台、标题、作者（可见时）、直接 URL、gap、复用点、边界和状态；CSV 可以作为单一备份附件。这样 CSV 卡片无法打开时仍有规范 URL 可去重。最多 10 条时正文可承载，不需要额外 MD。
- **ZIP 结构若将来另行验证：**`manifest.json + candidates.csv + rejected.csv + summary.md + next_gaps.json`。在确认当前下载链能稳定下载、文件能读之后再采用；本轮没有验证，因此现在不依赖 ZIP。

# 13. STOP POLICY

1. **正式硬停止：**五方向都到 20/20（总计 100）即停止新搜索；只做收尾去重/对账，不再把 gap 变成新的 batch。
2. **有界 reserve：**只有用户明确要求继续时才开 reserve；默认总上限 **20 条**（每方向最多 4 条），到线即停。这里 18 条 reserve 已经在 quota 完成时存在，后面最多再补 2 条就应停。
3. **边际收益停止：**任一方向连续两批每批新增少于 2 条，或留存率低于 20%，停止该方向并报告。B10 已触发低留存信号。
4. **重复/筛除停止：**连续两批 worker 历史重复超过 30%，或明显筛除超过 60%，先暂停该方向；一次重定向后仍触发则停止。
5. **gap 不扩权：**候选阶段 gap 只能排序已有候选，不能因“仍有未验证集成”自动延长搜索。需要实际证明的 gap 留到 SECOND PASS。
6. **异常门槛：**严重错题、坏格式无法解析、发送幂等性不明、真实浏览器 session 不能恢复、或必须由用户决定价值取舍时暂停对应 lane；另一条 lane 可继续。

# 14. 如果重新跑这次任务

实际发生的是 100 项正式目标加上持续 reserve，最后计入 221 个候选；因此“原样复跑 221”本身没有天然终点，不能诚实给出固定工期。我按有界、可复现的任务口径估算：**100 项正式目标 + 最多 20 项 reserve、两 lane 常驻、一个主结果文件、无深审**。当前 26:01 的墙钟和 6–10 小时活动估计作为基线；优化后的区间是：

| 情景 | Wall-clock | 协调端 active | 假设 |
|---|---:|---:|---|
| Best-case | 4–6 小时 | 3–4 小时 | 扩展稳定、回包顺利、每批一次取件、严格停止在 reserve cap |
| Expected | 7–10 小时 | 4–6 小时 | 少量等待/一次附件故障，但无长时间断联；worker 仍按当前实测速度运行 |
| Conservative | 12–18 小时 | 6–9 小时 | 一次共享扩展恢复、一个 worker 附件需要正文回退、批次回包较慢 |

这些不是保证；worker 侧模型速度和未来浏览器服务状态不可控。若坚持重复收集到 221 条，任务量不等于原始 100 配额，以上估计不适用；应先明确总上限，而不是把每次发现的新 gap 当成永久工期。

# 15. What I did well

- **RUN_ID 与精确线程识别值得保留。**B04–B10 的 prompts 都有独立 RUN_ID，发送前后通常核对线程身份；DOT B06 的确认延迟后刷新、等待并找到同一消息，没有重复发。Muse B04 有一次同 RUN_ID 的 retry 提交，说明幂等检查仍要硬化，不能把做了 RUN_ID 等同于每次都安全。
- **确实用上了两个 worker。**DOT 搜 GitHub、Muse 搜 X/YouTube；X 不可用时 Muse 继续 YouTube，没有因此整批停摆。B07–B10 多次出现一边运行时另一边已接到新 batch。
- **最终遵守了 candidate light-review 边界。**候选只按方向、直链格式和 canonical 去重暂存为 `CANDIDATE_UNVERIFIED`；没有把搜索说成实测，也没有在这一阶段做 PoC、字幕抓取或逐项 license 审计。
- **去重和计数分层总体可追溯。**V1、当前 V2、本批重复分开记录；221 候选与总账 232 行可由 11 条非计数/条件/拒绝记录解释；Muse B10 直链拿不到时没有猜 URL 或硬记入池。
- **恢复时保持了边界。**连接短暂恢复后只核对准确 Muse/DOT_WORKER 页面并取回公开结果；连接再失败时没有用 In-App Browser、协调端搜索或另一个 worker 偷换流程。
